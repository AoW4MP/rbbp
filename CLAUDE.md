# CLAUDE.md — контекст проекта для AI-агентов

Этот файл читается автоматически агентскими инструментами (Claude Code и подобными) при работе с этим репозиторием. Он содержит накопленный контекст по архитектуре, известным багам локализации/вёрстки и особенностям деплоя — чтобы не проходить весь путь анализа заново в каждой новой сессии.

**Важно:** документ описывает состояние на момент последнего обновления (см. раздел 7, чеклист) — репозиторий мог измениться с тех пор (мейнтейнер регулярно обновляет данные, версии `1.7.x`). Начинай работу со свежего `git clone`/`git log`, а не с доверия этому файлу как абсолютной истине.

### Архитектура (важно для быстрого старта)

Чистый JS + jQuery, без сборки/бандлера, без Node на клиенте. Данные — JSON.

```
index.html → HTML/header.html (общий хедер, подключается фетчем)
Data/Init.js  — загрузчик, подключает всё нижеперечисленное по цепочке
Data/src/
    dataloader.js   — ЯДРО: GetAllData(), CheckData(), все Sanitize*-функции (см. раздел 3)
    lookuputils.js  — findBy(), buildLookupMap()
    settings.js     — язык/тема, localStorage
    tooltips.js
Data/Builder.js      — САМЫЙ БОЛЬШОЙ файл (~7000+ строк), рендер карточек юнитов/заклинаний/абилок/книг/героев
Data/Faction.js       — конструктор фракций (Faction Creator)
Data/Search.js        — общий поиск
Data/Hero.js / HeroBeta.js / Forge.js — герой-билдер, кузница предметов
HTML/*.html           — по одной странице на раздел, у некоторых свой inline-скрипт (напр. Abilities.html)
Style/style.css, Style/icons.css
```

**Данные:**
- `Data/EN/*.json`, `Data/RU/*.json` — по 17 файлов, идентичный набор имён (`Units.json`, `Spells.json`, `Abilities.json`, `Tomes.json`, `Traits.json`, `HeroSkills.json`, `HeroItems.json`, `SiegeProjects.json`, `StructureUpgrades.json`, `StatusEffects.json`, `Destinies.json`, `Governance.json`, `EmpireProgression.json`, `ItemForgeTypes.json`, `ItemForgeUpgrades.json`, `UI.json`, **`all.json`** — самый важный, общий словарь концептов, ~19-20 тыс. записей, ~7+ МБ).
- `Data/GEN/*.json` — **общие для всех языков** файлы (не локализуются отдельно): `WorldStructures.json`, `FactionCreation.json` (культуры/классы/происхождения правителей), `UI.json`, `DestinyTraits.json` и др. Текстовые описания для GEN-сущностей всё равно тянутся из `all.json` через поле `extraLookup`/`extraLookup2`.
- Данные загружаются так: `window[key]` = всегда EN (`jsonUnits`, `jsonSpells`, ...), `window[key + "Localized"]` = выбранный язык (`jsonUnitsLocalized`, ...). Это ключевой паттерн для всех багов "показывает EN вместо RU".

**Сопоставление EN↔RU записей** — единого способа нет, зависит от файла:
- Юниты/заклинания и т.п. — обычно по `resid` (числовой ID, стабилен между языками).
- `Data/RU/*.json` часто содержит **испорченные `id`/`name`** (кириллица вместо слага, иногда с дублированием ед./мн. числа) — см. баги в разделе 2. НЕ доверяй полю `id`/`name` в RU-файлах как стабильному ключу.
- `Governance.json` — `resid` отсутствует вообще; единственный надёжный способ — **позиционный индекс массива** (проверено: EN/RU одинаковой длины и порядка).
- Некоторые сопоставления в коде идут по `icon` (`.find(entry => entry.icon === X.icon)`) — **это может быть небезопасно**, если коды иконок повторяются у разных записей (нашли реальный баг на этом в Governance, см. раздел 2, пункт 6).

## 2. Полный каталог найденных и исправленных багов

Все патчи уже смёржены в `main` (на момент составления документа — коммит `cc78d06`, сверху ещё легли `1.7.2 EN`/`1.7.2 RU` данные от мейнтейнера, наши JS/CSS фиксы не задеты).

### 2.1. Дублирование имён юнитов (ед./мн. число слиты без разделителя)
- **Симптом:** `"ЛучницаЛучницы"` вместо `"Лучница"`.
- **Причина:** экспорт локализации RU/др. языков иногда склеивает singular+plural без разделителя, прямо в поля `name`/`id` (иногда и `evolve_target`).
- **Обнаружение:** `[а-яё](?=[А-ЯЁ])` — строчная кириллица сразу перед заглавной без пробела = 100% надёжный маркер шва (заглавные буквы в норме идут только после пробела/начала строки).
- **Фикс:** `Data/src/dataloader.js` → `splitDuplicatedLocalizedText()` + `SanitizeLocalizedNames()`, вызывается в `CheckData()`. Обрабатывает `name`/`id` (и `evolve_target`) для `jsonUnitsLocalized`, `jsonSpellsLocalized`, `jsonHeroItemsLocalized`, `jsonUnitAbilitiesLocalized`, `jsonHeroSkillsLocalized`, `jsonTomesLocalized`.
- **Охват:** проверено на всех записях Units.json (360/513 было испорчено) — 0 ложных срабатываний.

### 2.2. Утечка placeholder-мусора локализации (три разных формата!)
Это оказалось семейство из **трёх разных сырых форматов**, которые движок игры использует для грамматического согласования (падежи, число, род) и которые движок игры сам разрешает в реальном времени — статичный сайт этого не может и не должен пытаться:

1. **`<eventColor>{N}</eventColor>`**, приклеенный к слову через 1-3 буквы-кода (`a`,`f`,`m`,`n`,`l`,`x`,`p`,`c`): `Приверженность астралуn<eventColor>{1}</eventColor>x<eventColor>{2}</eventColor>`.
2. **Голый вариант без обёртки**: `Боевой духa{1}n{2}` — самый массовый вариант, тысячи вхождений в описаниях абилок/статус-эффектов.
3. **`<<MARKER:content>>`** — макрос падежа/модификатора: `<<dat,c:<hyperlink>Мана</hyperlink>>>`. MARKER — комбинация падежного кода (`nom/gen/dat/acc/ins/pre`) и/или модификатора (`c/cm/m/mc/...`), **вариантов оказалось на порядок больше**, чем 6 падежей — регэксп обобщён до `[a-zA-Z,]*:` вместо перечисления комбинаций.
4. **`"singular||plural"`** — склейка через явный разделитель `||` (более "цивилизованный" вариант дублирования, чем п.2.1) — в основном встречается в `all.json`.

- **Важно НЕ путать** с похожим, но принципиально другим и **умышленно нетронутым** макросом: `<<Word<eventColor>{вариант1/вариант2}</eventColor>>>` (выбор по роду персонажа, напр. `<<PlayerLeader<eventColor>{осторожен/осторожна}</eventColor>>>`) — у него **нет двоеточия** после префикса, это отличает его от падежного макроса. Он завязан на живое состояние игры (пол персонажа/переменные типа `EventHouseLord.TitleName`), статически неразрешим в принципе, трогать не нужно.
- **Фикс:** `Data/src/dataloader.js` → `sanitizeLocalizationMacros()` + `SanitizeAllFromPO()`. Применяется **один раз, глобально, ко всем строковым полям** `jsonAllFromPOLocalized` сразу после загрузки (не патчит каждого из ~30 мест чтения `all.json` по отдельности — это осознанное архитектурное решение).
- **Порядок операций внутри `sanitizeLocalizationMacros`:** `split("||")[0]` → развернуть `<<...:content>>` в `content` → срезать цепочки `буква{цифра}`/`буква<eventColor>{цифра}</eventColor>` → срезать одиночные голые буквы-суффиксы без цифры.
- **Валидация:** регрессия прогонялась на ВСЕХ 77 027 строковых значениях реального `Data/RU/all.json` — 21 229 изменено, 0 разбалансированных `<hyperlink>`-тегов, 0 ложных срабатываний на легитимных `<eventColor>{amount}</eventColor>`-подобных значениях.
- **Осознанно НЕ покрыто:** голые `<<Word<eventColor>{A/B}</eventColor>>>` (см. выше) и `<<CASE:Variable.Path>>` (динамические игровые переменные типа имени расы/титула игрока в квестовом тексте) — структурно другая, принципиально нерешаемая для статического сайта проблема, есть и в EN тоже.

### 2.3. Battled иконки заклинаний призыва (SummonIcons)
- **Симптом:** `Icons/SummonIcons/Призыв_поборника.png` — 404, кириллическое имя файла.
- **Причина:** `Data/Builder.js`, функция `showSpell()` — для заклинаний из списка `incorrectIconOverrideList` (11 штук, у них `icon`-поле в данных указывает на заведомо неверную картинку) код брал имя файла из **локализованного** объекта заклинания (`spellFound.id`), а не из EN (`spellFoundEN.id`). Файлы в `Icons/SummonIcons/` названы только по EN-слагу.
- **Фикс:** одна строка — `spellFound.id` → `spellFoundEN.id`.
- **Проверено:** все 11 заклинаний из `incorrectIconOverrideList` имеют файл под правильным EN-именем.

### 2.4. HeroGovernance.html показывал EN вместо RU
- **Причина:** `jsonHeroGovernanceLocalized` **вообще ни разу не использовался** во всём коде — `findHeroGovernance()` всегда брал `jsonHeroGovernance` (EN).
- **Особенность сопоставления:** `resid` в `Governance.json` отсутствует у всех записей; сопоставление по `icon` (как это сделано для соседней фичи Hero Ambitions через `.find()`) **небезопасно** — несколько губернаторов делят один код иконки, `.find()` вернул бы текст не того губернатора. Единственный надёжный способ — **позиционный индекс массива** (проверено вручную по всем 19 записям — порядок идентичен).
- **Фикс:** `jsonHeroGovernance[j]` → `jsonHeroGovernanceLocalized[j]` в `findHeroGovernance()`.
- **НЕ трогали:** вторая функция `CheckIfFromGovernance(unitName)` тоже читает `jsonHeroGovernance` — но она ищет EN-имя юнита в EN-тексте для кросс-ссылок, это корректное поведение, не баг.

### 2.5. Ложный «замочек» в EmpireTree (General, уровень 60)
- **Симптом:** между «Строительство дорог» и «Раскопки» показывается иконка замка, будто это взаимоисключающий выбор.
- **Причина:** `HTML/EmpireTree.html`, логика "если два неповторяемых перка (`repeat_cost_increase === undefined`) имеют одинаковый `required_level` — рисуем замочек" — эвристика в принципе неверна для этого дерева: в данных **нет** поля `excludes`/`choice_group`, подтверждающего реальное взаимоисключение. Это просто совпадение уровня разблокировки у двух независимых перков.
- **Важный нюанс, чуть не приведший к регрессии:** в коде уже был похожий hardcoded-список исключений (`Wizard King`, `Mana Extraction`, `Indomitable Defenders`) — но та ветка **полностью скрывает узел** из дерева, а не просто убирает замочек! Если добавить туда же `Road Building`/`Excavation`, они пропали бы с дерева целиком — это НЕ то, что нужно. Правильный фикс — отдельное условие, скрывающее только сам `<img class="lock">`, не трогая рендер узла.
- **Фикс:** добавлено условие `jsonEmpire[i].name !== "Road Building" && jsonEmpire[i].name !== "Excavation"` именно в блок, создающий `testLock`.

### 2.6. Обновление описаний 5 лидеров (Ruler Origins)
- Не баг, а контент-задача: пользователь вручную отредактировал описания Героя/Короля-волшебника/Повелителя драконов/Тёмного повелителя (Eldritch Sovereign)/Короля великанов в `Data/EN/all.json` / `Data/RU/all.json` (поле `id` = `TRAITS_BACKGROUND_CHARACTERS@MAIN_TYPE@RACIAL_LEADER` / `...WIZARD_KING` / `DLC@DRAGONLORDS@...@DRAGON_LEADER` / `DLC@ELDRITCHREALMS@ELDRITCH_RULER_TYPE` / `DLC@GIANTKINGS@...@GIANT_KING`).
- **Важная находка по ходу:** в черновике пользователя для «Героя» был синтаксис `{GLOBAL.X.Hyperlink}` + самозакрывающийся `<bullet/>` — этот формат **нигде больше не встречается рабочим** во всём `all.json` и **не обрабатывается никаким JS-кодом сайта** (проверено: `grep -rn "GLOBAL\." Data/*.js` — пусто). Заменено на реальную конвенцию сайта (`<hyperlink>Text</hyperlink>` + иконки `<gold></gold>`/`<happiness></happiness>`/`<unitprod></unitprod>`), подтверждённую по существующим рабочим примерам тех же понятий (City Stability, Gold, Throne City) в том же файле.

### 2.7. Визуальные баги вёрстки (перенос длинных RU-названий)
Два похожих, но разных по механике случая:

- **Выпадающие меню шапки** (`#menu ul.menus` в `Style/style.css`) — ширина 180px, шрифт 12px, унаследовано из `aow4db` без изменений (работает для EN просто потому что слова короче). ## 3. Переиспользуемый инструментарий (regex/код), уже проверенный на реальных данных

Всё это уже лежит в `Data/src/dataloader.js` в `main`, но полезно иметь под рукой как справочник при поиске НОВЫХ багов той же природы:

```js
// Шов дублирования ед./мн. числа (строчная кириллица встык с заглавной)
const DUPLICATED_NAME_SEAM = /[а-яё](?=[А-ЯЁ])/;

// Полный конвейер очистки макросов локализации (all.json и подобные источники)
function sanitizeLocalizationMacros(value) {
    if (typeof value !== "string" || value.length === 0) return value;
    value = value.split("||")[0];
    value = value.replace(/<<[a-zA-Z,]*:(.*?)>>/g, "$1");
    value = value.replace(
        /(?<=[а-яёА-ЯЁ])(?:[a-zA-Z]{1,3}(?:<eventColor>\{\d+\}<\/eventColor>|\{\d+\}))+/g,
        ""
    );
    value = value.replace(/(?<=[а-яёА-ЯЁ])[afmnlxpc]{1,3}(?=<|\s|$|[.,;:!?)])/g, "");
    return value.trim();
}
```

**Известные грани применимости (не расширять бездумно):**
- Требует lookbehind (`(?<=...)`) — ES2018+, нормально для браузеров, но проверяй если код когда-то пойдёт через старый транспайлер.
- Буквенный набор `[afmnlxpc]` — **закрытый список**, основанный на реально встреченных кодах. Если найдёшь новый код-букву, добавляй в список только после проверки, что она не встречается в реальных словах (Cyrillic+буква не бывает штатно).
- НЕ трогает `<<Word<eventColor>{A/B}</eventColor>>>` (без двоеточия после префикса) — это осознанно, не баг регэкспа.

**Методология поиска масштаба бага** (использовалась многократно, работает хорошо):
```python
import json, re
data = json.load(open('Data/RU/all.json'))  # или любой другой файл
pattern = re.compile(r'...')
count = sum(1 for d in data for v in d.values() if isinstance(v, str) and pattern.search(v))
```
Всегда считай масштаб (сколько записей затронуто) ПЕРЕД тем как чинить — это определяет, точечный ли фикс нужен или архитектурный (санитайзер у источника).

## 4. Установленный workflow для этого проекта (использовать и дальше)

1. **Клонировать свежую копию** перед началом анализа (`git clone`, не полагаться на старый локальный чекаут — за сессию это несколько раз приводило к `rejected` push из-за устаревшего `origin/main`).
2. **Анализ:** найти root cause на уровне кода/данных, показать конкретные примеры (`repr()` сырых строк), посчитать масштаб (сколько записей затронуто).
3. **Сравнение с `aow4db`** — полезно, чтобы понять "это унаследованная особенность" vs "баг конкретно нашего форка/баланс-мода".
4. **Патч:** делать изменения точечно, проверять `git diff --stat` перед коммитом — если diff неожиданно большой (реформатирование целого файла), значит где-то потерян оригинальный стиль форматирования (для `all.json` — `json.dumps(data, indent=2, ensure_ascii=False)` воспроизводит файл побайтово, это подтверждено).
5. **Валидация перед коммитом:**
   - `python3 -c "import json; json.load(open(f))"` для всех тронутых JSON.
   - `node --check file.js` для JS.
   - Регрессия regex на РЕАЛЬНЫХ данных (не выдуманных примерах) — где возможно, на ВСЕХ записях файла, а не выборке.
6. **Коммит** с подробным сообщением (что, почему, как проверено, что осознанно не тронуто и почему).
7. **Патч-файл:** `git format-patch -1 HEAD --stdout > NNNN-description.patch`.
8. **Обязательная проверка патча на чистом клоне** (`git clone` в отдельную папку → `git am патч.patch` → проверить `exit code 0` + содержимое) — это НЕ опционально, несколько раз спасало от отправки нерабочего патча.
9. Пользователь применяет патч сам через `git am` + `git push` (у Claude в вебе нет прямого push-доступа — если в новой сессии Claude Code он есть, это меняет процесс: можно коммитить и пушить напрямую, но валидацию перед пушем всё равно стоит сохранить как привычку).

## 5. Сага про нестабильный GitHub Pages деплой — статус и как не наступать на те же грабли

**Симптом:** `deploy`-шаг `pages-build-deployment` падает с generic `Deployment failed, try again later.` на стадии `syncing_files`, при этом `build`-джоба (сборка артефакта) всегда проходит успешно.

**Собранные доказательства (важно, чтобы не тратить время на переисследование):**
- Падает на **пустых** коммитах (`git commit --allow-empty`) — содержимое коммита ни при чём.
- Падает после **отката** (revert) — тоже не о содержимом.
- Падает при **ручном импорте файлов** через веб-интерфейс (не git push вообще).
- Debug-логи (`ACTIONS_STEP_DEBUG=true`/`ACTIONS_RUNNER_DEBUG=true`, включены через Settings → Secrets and variables → Actions → Variables) **не дают никакой дополнительной информации** — сам экшен `deploy-pages@v5` не получает от бэкенда GitHub Pages ничего, кроме этого же generic-сообщения.
- Размер артефакта (~484-510 МБ, из них `Icons/` — 426 МБ) **не коррелирует** с успехом/провалом — идентичный размер был и у успешных, и у провальных запусков.
- **Важное сравнение:** оригинальный `aow4db` (даже БОЛЬШЕ по размеру — 635 МБ против 533 МБ у rbbp, полный набор языков) с идентичным конфигом (`.gitattributes`, `.gitignore`, `.nojekyll`, `_config.yml` — побайтово совпадают) имеет 385 успешных прогонов подряд без видимых сбоев. Это сильный аргумент, что проблема специфична именно для деплой-окружения `rbbp`/аккаунта `AoW4MP`, а не общая для больших статических сайтов на Pages.
- Официальный статус GitHub (`githubstatus.com`) в моменты сбоев показывал «Operational» — не публично признанный инцидент.

**Что уже сделано:**
- Открыт тикет в GitHub Support с полным описанием и списком ID неудачных деплоев. Ответ саппорта подтвердил корректность диагностики (see выше) и посоветовал отправить тикет на бэкенд-ревью — сами логи бэкенда Pages не самообслуживаемы, нужен саппорт.
- Рабочий тактический обход (не решение первопричины): при зависании/провале — **простой пустой коммит-ретриггер** почти всегда в итоге проходит (иногда с первой попытки, иногда нужно 2-3).
- **Важно:** при toggle `Settings → Pages → Source → None → сохранить → обратно на main → сохранить` (это НЕ кнопка "передеплой", а буквально снятие с публикации и повторная публикация) — один раз это привело к тому, что сайт **лёг (404)**, пока новый деплой не прошёл. Не делать это бездумно, если сайт уже работает на старой версии — лучше молча ретриггерить пустым коммитом, чем рисковать даунтаймом.

**Если в новой сессии Claude Code есть прямой доступ к VM с более мощными правами** — стоит проверить:
- `Settings организации AoW4MP → Billing and plans` — не подошли ли к лимиту хранилища/трафика Pages (единственная непроверенная сама-по-себе гипотеза, требует прав уровня организации, которых не было в вебе).
- Статус открытого тикета в GitHub Support.
- Если проблема продолжится — рассмотреть вынос `Icons/` (426 МБ, доминирующая часть размера) из паблиш-скоупа Pages в отдельный CDN/Release assets, чтобы снизить размер публикуемого артефакта — это НЕ подтверждённая причина, но снижает риск на будущее.

## 6. Потенциальные направления для дальнейшей работы (не проверено / не завершено)

Зафиксировано по ходу сессии, но осознанно НЕ тронуто — стоит держать в уме для будущего анализа:

1. **`evolve_target`-подобные поля с тем же паттерном дублирования** в других файлах, кроме Units.json — стоит перепроверить после каждого обновления дампа данных (мейнтейнер регулярно обновляет `Data/EN|RU/*.json`, последний раз — версия 1.7.3, см. раздел 6.1).
2. **Описание (`description`) юнитов** в Units.json содержит редкие остатки мусора (`"Тень^F"` и т.п.) — это МЁРТВЫЕ данные (поле нигде не рендерится в UI), чинить не стали, но если когда-нибудь это поле начнут использовать — вспомнить про этот нюанс.
3. **~30 мест кода**, читающих `jsonAllFromPOLocalized` напрямую в обход `LocalizeUI()` (Builder.js, Faction.js, PantheonTree.html, RealmTraits.html, Search.js) — общий санитайзер (`SanitizeAllFromPO()`) их все покрывает, но если будет реструктуризация кода — не забыть, что это единая точка правки, не 30 отдельных.
4. **Faction.js, ~строки 1874-1897 и 1968-1990** — код, читающий поле `spell_slug` из записей `Traits.json`, которого **не существует ни в EN, ни в RU файле** — мёртвый, недостижимый код с текущими данными. Не трогали, но если когда-то в данных появится это поле — там тоже потенциально есть тот же паттерн бага (использование локализованного id вместо EN-слага для построения пути к иконке), что и был в п. 2.3.
5. **`<<Word<eventColor>{A/B}</eventColor>>>` гендерный макрос** и **`<<CASE:Variable.Path>>` динамические игровые переменные** в квестовом/дипломатическом тексте (истории структур, событий) — принципиально нерешаемо для статического сайта, но если появятся жалобы именно на ЭТИ страницы (сюжетные тексты структур, дипломатия) — это ожидаемо и не баг нашего кода, а фундаментальное ограничение (то же самое и в EN).
6. **Новые дампы данных от мейнтейнера** — после каждого такого обновления стоит прогонять regex-проверки из раздела 3 заново (методология: посчитать масштаб паттернов по всем полям всех JSON, не гадать точечно). Статус на данный момент — см. 6.1.
